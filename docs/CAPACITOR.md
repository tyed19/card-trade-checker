# FairSwap native shell (Capacitor) — how it works

Phase 1 of the store-launch plan (`fairswap-store-launch-checklist.md`
in the workspace, not this repo).

## The architecture decision: remote-URL mode

FairSwap is a **server-backed** Next.js app. Card identification runs
server-side (CLIP picture matching against a 25k-vector index, OCR
workers, catalog APIs in `app/api/*`). A static export — Capacitor's
default "bundle your web build" mode — **cannot be the product**:
there would be no `/api/identify` to scan a card against.

So the shell ships in **remote-URL mode**:

- `capacitor.config.ts` sets `server.url` to the live deployment
  (`https://card-trade-checker.vercel.app` by default; override with
  `CAP_SERVER_URL=… npx cap sync` for a preview/staging shell).
- The native apps are a thin, branded wrapper: FairSwap icon + splash,
  the real device camera, a verdict haptic, the native share sheet —
  loading exactly the web app everyone already uses.
- `webDir` points at `native-shell/`, a single static splash page
  (brand mark + "couldn't reach the internet, tap to try again"). It
  is **not** the app; it only surfaces if the remote app is
  unreachable.

**The tradeoff, honestly:** beta-appropriate, and for this product
mostly upside — one codebase, every web fix (including identification
improvements) reaches the apps the moment Vercel deploys, no store
re-review for content changes, no fork to maintain. The costs: the
apps need connectivity to do anything (true of the product anyway —
identification is server-side), and a future fully-bundled mode
(hybrid: local UI + remote APIs) remains a separate decision if
offline binder browsing ever becomes a requirement. The binder itself
already lives on-device in localStorage in both modes.

## The native bridge (`lib/native.js`)

The web app feature-detects the shell and enhances; it never requires
it. Every export is guarded and inert in a plain browser:

- `isNative()` — `window.Capacitor?.isNativePlatform?.() === true`.
- `takeNativePhoto()` — Capacitor Camera plugin → `File`. Used by both
  photo entry points (the trade panels in `app/page.js` and the binder
  scan session in `app/binder-ui.js`) via their photo buttons. The
  returned file enters the **existing** pipeline untouched
  (`shrinkForUpload` → FormData → `/api/identify`), so the 2400px /
  JPEG-q90 contract holds on both paths. Plugin settings: `quality: 90`
  (matches q90), `width: 2400` (matches the max upload dimension; the
  in-page shrink stays as a no-op safety net), `correctOrientation:
  true` (keeps the EXIF sideways-photo trap out of the native path).
  Return contract: a `File` on success, the string `'cancelled'` if
  the user backed out (callers do nothing — no fallback picker on top
  of a cancelled camera), and `null` on any other failure (not native,
  permission denied, plugin error) — callers then click the hidden
  `<input type="file">` **exactly as the app behaved before Capacitor**.
- `verdictHaptic()` — light `Haptics.impact` when a FAIR verdict
  lands. Failures swallowed.
- `nativeShare({title, text, url})` — native share sheet where a call
  site offers it; returns false (browser/cancel/error) so callers keep
  their copy-link fallback.

Plugins are `import()`ed dynamically inside the functions, so a
browser session never downloads or executes them.

## Icons & splash

Sources in `assets/` were rendered from the final brand vectors per
`usage-spec.md`: iOS icon = full mark on a full-bleed Cream field
(1024×1024, no alpha); Android adaptive = reversed mark foreground
(art inside the ~76% maskable safe zone) over a Deep Teal `#00596B`
background layer; splash = reversed mark centred on Deep Teal.
`npx capacitor-assets generate` produced the platform sets (iOS
AppIcon + universal Splash imageset; Android mipmaps incl.
`mipmap-anydpi-v26` adaptive XML). Regenerate after a brand change:

```bash
node scripts/make-native-assets.mjs   # needs the brand folder (path arg if moved)
npx capacitor-assets generate
# then delete the PWA extras it also writes (icons/, public/manifest.webmanifest)
```

## Build / run locally (Tye's Mac)

Web app (unchanged):

```bash
npm install && npm run build && npm start
```

Native shell:

```bash
npm install
npx cap sync            # copies native-shell + config into ios/ and android/
```

**iOS:** open `ios/App/App.xcodeproj` in Xcode → select your team
(signing) → run on device/simulator, or Product → Archive for
TestFlight. Requires an Apple Developer account (exists — Koti) and
the App Store Connect app record (Phase 2, below).

**Android:** open `android/` in Android Studio → Run, or Build →
Generate Signed App Bundle for Play. The release keystore is a
Phase 3 step tied to the Play Console account (below).

**CI proofs:** Actions → "Native shell builds" → Run workflow →
android / ios / both. Android builds an unsigned release AAB + a debug
APK (artifact attached); iOS archives with signing disabled. Neither
needs any secret.

## What remains blocked on Tye (signing & accounts)

Everything below is account-side; the code and projects are ready.

1. **Apple signing + App Store Connect record** — create the FairSwap
   app record (bundle ID `app.fairswap`), select the developer team in
   Xcode, first TestFlight upload. (Developer account exists.)
2. **Android upload keystore** — generate the release keystore **once**
   (Android Studio wizard or `keytool`), store it + passwords in the
   password manager, and back it up: Google cannot recover a lost
   upload key for a new app enrollment without a reset process, and
   the *app signing* key is forever. Deliberately NOT generated in
   this phase or committed anywhere.
3. **Play Console app record** — the Play Console account exists
   (confirmed 2026-10-18); the FairSwap app record + closed testing
   track are Phase 3 items, along with the 12-tester / 14-day
   production-eligibility clock.
4. **Public-launch gates** (unchanged from the checklist, not beta
   blockers): attorney's USPTO clearance, licensed price-data source,
   seller entity for store tax/banking.
